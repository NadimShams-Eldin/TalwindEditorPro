# ADR-0002: نطاق v1 — HTML ثابت + Tailwind CSS v4

- **الحالة:** مُعتمد
- **التاريخ:** 2026-11-01
- **المُعتمد:** مالك المنتج (Nadim Shams Eldin)
- **القرار المرتبط:** D-02
- **يُغلق قبل:** المرحلة 1

## Context

كل إطار أو منصة إضافية تضاعف تعقيد ثلاثة أشياء في وقت واحد: نموذج التحرير، وخط أنابيب البناء، واختبارات الأمانة البايتية. المشروع يقوم على وعد واحد صارم: «نعدّل ما تكتبه، ولا نعيد كتابته». هذا الوعد قابل للتحقق فقط عندما يكون المصدر نص HTML نراه كاملًا.

كذلك، Tailwind v4 غيّر نموذج الإعداد جذريًا: الثيم أصبح CSS-native عبر `@theme`، والمحرك أصبح حزمة JS (`@tailwindcss/node`) لا مجرد PostCSS plugin. دعم v3 وv4 معًا يعني مسارين للثيم والمرشحات والبناء.

## Decision

نطاق v1 هو:

1. **HTML ثابت** كمدخل ومخرج. ملفات `.html` تُفتح وتُحفظ كما هي بايتيًا.
2. **Tailwind CSS v4** كمحرك التنسيق الوحيد.
3. **مشاريع v3** تُرفض بوضوح عند الاستيراد مع تقرير سبب، ولا تُحاوَل بصمت.

خارج النطاق صراحةً في v1:

- React / Vue / Svelte / Astro / Next.
- WordPress وأي CMS.
- SASS/LESS أو أي معالج CSS مسبق.
- Tailwind v3.
- JSX/TSX وملفات المكونات.

## Alternatives

1. **Tailwind v3 وv4 معًا:** يوسّع السوق، لكنه يضاعف مسار الثيم والمرشحات ويؤجل parity.
2. **دعم React مبكرًا:** يفتح أكبر شريحة، لكنه يهدم ضمان البايتات (JSX ليس HTML نصيًا) ويستلزم AST خاصًا بكل إطار.
3. **دعم CMS مبكرًا:** يعتمد على قوالب ديناميكية، ما يناقض التصدير النظيف.

## Consequences

**إيجابي:**
- ضمان بايتي قابل للقياس والاختبار على 100% من ملفات v1.
- مسار بناء واحد، فاختبارات parity تعني شيئًا.
- رسالة منتج واضحة: «محرر HTML + Tailwind v4».

**سلبي:**
- شريحة أصغر من «كل من يستخدم Tailwind».
- من يستخدم v3 يجب أن يهاجر أولًا.

**المخاطر:**
- R-05 (سوق أصغر من المتوقع): تُعالَج بمقابلات Phase 0 قبل P3، وبإمكانية توسيع النطاق في v2 دون كسر النواة.

## Invariants

أي ميزة مستقبلية تُضاف يجب ألا تكسر هذه الثوابت:

- الحفظ لا يمر عبر `parse + serialize`.
- التصدير لا يحتوي `data-tep-*` ولا أي metadata.
- المعاينة تستخدم نفس محرك Tailwind المستخدم في التصدير (نفس الإصدار المثبت).
