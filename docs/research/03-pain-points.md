كل مشكلة لها:

- **الوصف**: ما يحدث فعلًا.
- **الدليل**: مصدر أو وسم.

- **الحلول الحالية**: ما يفعله المطورون اليوم.
- **الفرصة**: ما يمكن لمنتجنا فعله.
- **معيار القبول**: كيف نعرف أننا حللناها.

الوسوم: `[موثق]` من وثائق رسمية، `[مستنتج]` استنتاج، `[فرضية]` يحتاج تحققًا، `[سوق]` ملاحظة سوقية.

## 3. المشكلات بالتفصيل

### P-01: class soup وصعوبة القراءة

**الوصف:** عنصر واحد يحمل 15-30 class، وتصبح قراءة البنية والتعديل اليدوي صعبة، خصوصًا مع variants.

**الدليل:** `[موثق]` Tailwind itself يعترف بأن النهج "يخالف أفضل الممارسات التقليدية" لكنه يقدم مزايا. `[فرضية]` شكاوى المطورين من "class soup" شائعة في المجتمع.

**السبب الجذري:** التنسيق موزع على classes، ولا توجد طبقة تجريد إلزامية. المكونات في React/Vue تحل جزءًا، لكن static HTML وWordPress لا يملكان نفس النموذج.

**الحلول الحالية:**
- `@apply` أو component classes.
- Tailwind UI / مكونات جاهزة.
- Prettier plugin لترتيب classes.
- tailwind-merge.
- قوالب framework.

**الفرصة:**
- عرض العنصر كـ "visual style summary" بدل نص طويل.
- كشف مجموعات classes المتكررة واقتراح استخراجها إلى مكوّن.
- وضع "class HUD" يعرض الخصائص الفعلية.
- تحرير دلالي (Spacing, Color) بدل إضافة class نصي.
- إخفاء/طي variants غير النشطة.

**معيار القبول:** يستطيع المستخدم فهم تنسيق عنصر من 20 class خلال أقل من 5 ثوانٍ، وتقليل عدد classes الظاهرة بنسبة 50% دون فقدان التحكم.

### P-02: الأصناف الديناميكية لا تولّد CSS

**الوصف:** class يُبنى بـ string concatenation أو props ديناميكية، فلا يراه scanner، فلا يُولد CSS.

**الدليل:** `[موثق]` Tailwind docs: "Don't construct class names dynamically".

**السبب الجذري:** scanner نصي لا يحلل الكود. حتى في المحرر البصري، إذا أضفت class إلى DOM ولم تُمرره للمحرك، فقد لا يُولد.

**الحلول الحالية:**
- كتابة classes كاملة.
- mapping objects.
- safelist.
- `@source inline()`.

**الفرصة:**
- بناء candidate set من AST المحرر + الملفات.
- تمرير candidates مباشرة إلى Tailwind.
- كشف class مستخدم بلا CSS وتقديم إصلاح تلقائي.
- تحذير عند كتابة class ديناميكي في code editor.

**معيار القبول:** صفر حالات "class موجود لكن لا تأثير" في مشروع اختباري يضم 100 تعديل ديناميكي.

### P-03: تعارض الأصناف وترتيبها

**الوصف:** `p-4` و`p-6` معًا، أو `bg-red-500` و`bg-blue-500`، والفائز غير متوقع.

**الدليل:** `[موثق]` Tailwind لا يمنع التعارض. `[سوق]` tailwind-merge شائع لحل المشكلة.

**السبب الجذري:** classes ليست خصائص CSS مباشرة، وترتيبها في HTML لا يحدد الأولوية.

**الحلول الحالية:**
- tailwind-merge.
- Prettier plugin.
- انضباط يدوي.
- مكونات مغلقة.

**الفرصة:**
- ConflictResolver مدمج في الـ IR.
- عند إضافة class، إزالة المتعارض تلقائيًا ضمن نفس variant scope.
- عرض "لماذا هذا class فائز".
- منع `!important` العشوائي.

**معيار القبول:** 100% من عمليات التعديل البصري لا تترك class متعارضًا في نفس scope.

### P-04: تعقيد الثيم وتعدد مصادر الحقيقة

**الوصف:** الثيم موزع بين `@theme`، config قديم، CSS variables، Design Panel، Figma، وقيم arbitrary.

**الدليل:** `[موثق]` Tailwind v4 نقل الثيم إلى CSS، مع توافق `@config`. `[موثق]` Pinegrow Design Panel يعدل الثيم، لكن حذف/إعادة تسمية لون لا يعدل HTML.

**السبب الجذري:** لا يوجد token graph مركزي يربط التصميم بالكود. كل أداة تعرف جزءًا.

**الحلول الحالية:**
- ملف theme واحد.
- قواعد فريق.
- Style Dictionary.
- مراجعة يدوية.

**الفرصة:**
- Token graph مع impact analysis.
- ثيمات متعددة (light/dark/brand).
- مزامنة Figma variables.
- منع القيم الخارجة عن النظام إلا باستثناء موثق.
- عرض "أين يُستخدم هذا الـ token".

**معيار القبول:** تغيير token واحد يحدّث كل الاستخدامات في المشروع في أقل من ثانية، مع تقرير impact قبل التطبيق.

### P-05: الاستجابة صعبة التصور والتحرير

**الوصف:** المستخدم يعدل `md:` ولا يرى بوضوح ما سيحدث على `lg`، أو ينسى أن القيمة موروثة من breakpoint أصغر.

**الدليل:** `[موثق]` Tailwind mobile-first. `[موثق]` Pinegrow يعرض القيم الموروثة بالأزرق، لكنه يحتاج تنقلًا بين الأجهزة.

**السبب الجذري:** نموذج cascade متعدد الأبعاد (breakpoint × state × variant) صعب على الواجهات النصية.

**الحلول الحالية:**
- فتح عدة page views.
- devtools.
- معاينة يدوية.

**الفرصة:**
- محرر inheritance يوضح مصدر كل قيمة.
- مقارنة breakpoints جنبًا إلى جنب.
- تحذير من overrides غير الضرورية.
- اقتراح أقرب breakpoint بدل تكرار القيم.
- محاكاة أجهزة دقيقة.

**معيار القبول:** يستطيع المستخدم معرفة أي breakpoint يتحكم في خاصية معينة دون فتح devtools.

### P-06: غياب تجريد مكونات أصلي

**الوصف:** Tailwind لا يقدم مكونات. في static HTML، إعادة الاستخدام صعبة، وفي React/Vue تحتاج بناء نظام مكونات.

**الدليل:** `[موثق]` Tailwind docs: "TailwindCSS differs from frameworks like Bootstrap in that it comes with no ready-made components".

**السبب الجذري:** Tailwind لغة utilities، وليس design system.

**الحلول الحالية:**
- Tailwind UI/Plus.
- مكونات framework.
- `@apply`.
- نسخ ولصق.

**الفرصة:**
- مكونات أصلية مع props وslots وvariants.
- استخراج مكون من تحديد.
- مزامنة المكونات عبر الصفحات.
- مكتبة مكونات خاصة بالفريق.
- تصدير مكونات كـ HTML/CSS نظيف.

**معيار القبول:** إنشاء مكون من عنصر موجود، واستخدامه في 10 صفحات، وتحديثه مرة واحدة، دون كسر editable areas.

### P-07: إعادة الهيكلة وتنظيف المشروع

**الوصف:** مشروع يكبر، classes تتكرر، CSS يتضخم، ولا توجد أداة تقترح تحسينًا.

**الدليل:** `[فرضية]` ألم شائع في المشاريع طويلة العمر.

**السبب الجذري:** لا توجد رؤية كلية للأنماط المتكررة والتبعيات.

**الحلول الحالية:**
- بحث يدوي.
- refactoring يدوي.
- linters.

**الفرصة:**
- كشف repeated class patterns.
- اقتراح استخراج مكون أو component style.
- كشف classes غير مستخدمة.
- كشف arbitrary values المتكررة التي يجب أن تصبح token.
- خطة إعادة هيكلة قابلة للتطبيق والتراجع.

**معيار القبول:** تقرير واحد يعرض أكبر 10 فرص لإعادة الهيكلة مع تقدير الأثر.

### P-08: تشتت build tools وإصدارات Tailwind

**الوصف:** Vite، PostCSS، CLI، standalone، CDN، إصدارات v3/v4، plugins، config قديم.

**الدليل:** `[موثق]` v4 غيّر الحزم والأوامر، وأزال `@tailwind` directives.

**السبب الجذري:** Tailwind نفسه أداة build، وليس مجرد CSS library.

**الحلول الحالية:**
- توثيق المشروع.
- upgrade tool.
- Docker/CI.

**الفرصة:**
- كشف تلقائي لإعداد المشروع.
- إدارة إصدار Tailwind لكل مشروع.
- تشغيل build في الخلفية مع عرض الحالة.
- adapter موحد للأوامر.
- أداة ترقية مدمجة.

**معيار القبول:** فتح مشروع v3 أو v4 وتشغيل المعاينة دون إعداد يدوي في 90% من الحالات.

### P-09: صعوبة معرفة سبب عدم تطبيق class

**الوصف:** class موجود لكن لا أثر. الأسباب: variant غير مفعل، الثيم لا يعرفه، CSS لم يُولد، specificity، أو class متعارض.

**الدليل:** `[موثق]` Pinegrow: variants غير المفعلة تظهر، والعلامة أنها بلا تأثير. `[موثق]` Tailwind: dynamic classes لا تولد.

**السبب الجذري:** عدم شفافية pipeline.

**الحلول الحالية:**
- devtools.
- حذف/إضافة يدوية.
- قراءة docs.

**الفرصة:**
- "Why isn't this applied?" panel لكل class.
- عرض candidate -> utility -> CSS rule -> computed style.
- إصلاح بضغطة: فعّل variant، أضف token، أزل التعارض.

**معيار القبول:** تشخيص أي class غير مطبق في أقل من 10 ثوانٍ.

### P-10: الجودة و accessibility بعدية

**الوصف:** المشاكل تُكتشف بعد البناء أو في المراجعة، وتكلفة إصلاحها أعلى.

**الدليل:** `[موثق]` Pinegrow 10 أضاف Page Health وAccessibility checks. `[فرضية]` معظم أدوات Tailwind البصرية لا تدمج ذلك في التحرير.

**السبب الجذري:** الجودة منفصلة عن نموذج التحرير.

**الحلول الحالية:**
- axe devtools.
- Lighthouse.
- مراجعة يدوية.

**الفرصة:**
- فحص أثناء التحرير على مستوى العنصر.
- منع إنشاء HTML غير صحيح.
- contrast checker مرتبط بالثيم.
- keyboard/focus checks.
- تقرير جاهز للعميل.
- إصلاحات مقترحة قابلة للتطبيق.

**معيار القبول:** مشكلة accessibility جديدة تظهر خلال ثانية من التعديل، مع إصلاح مقترح.

### P-11: التصدير النظيف من الأدوات البصرية

**الوصف:** الأدوات البصرية تُصدر HTML متضخمًا، classes زائدة، `data-*` داخلية، أو تعتمد على runtime.

**الدليل:** `[موثق]` Pinegrow يخزن class styles في `data-pg-class-style`، ويوصي بإزالتها عند النشر. `[مستنتج]` هذا يعني أن الكود المصدري ليس نظيفًا تمامًا.

**السبب الجذري:** الأداة تحتاج metadata، لكنها تضعها في الإخراج.

**الحلول الحالية:**
- تنظيف يدوي.
- build step.
- قبول التضخم.

**الفرصة:**
- فصل metadata عن الإخراج.
- export profile: "clean HTML" أو "with editor metadata".
- إزالة classes غير المستخدمة.
- تحسين الصور وCSS.
- تقرير حجم قبل/بعد.
- ضمان أن الناتج يعمل دون المحرر.

**معيار القبول:** موقع مُصدَّر لا يحتوي أي `data-editor-*` أو runtime خاص، وLighthouse performance >= 90 في قالب مرجعي.

### P-12: التعاون والمراجعة

**الوصف:** وكالة + عميل + مطور يعملون على نفس الموقع. الأدوات المحلية تعتمد Git، والأدوات السحابية تفرض منصتها.

**الدليل:** `[مستنتج]` Pinegrow محلي، ولا يوجد real-time collaboration موثق. Webflow/Framer سحابيان لكن بقفل أكبر.

**السبب الجذري:** نموذج الملفات المحلية لا يدعم التعاون الحي بسهولة.

**الحلول الحالية:**
- Git + PR.
- مشاركة شاشة.
- أدوات سحابية.

**الفرصة:**
- تعليقات ومراجعة مرئية على العناصر.
- revisions وvisual diff.
- سحابة اختيارية مع CRDT.
- صلاحيات (مطور/محرر محتوى/مراجع).
- تعاون غير متزامن أولًا، ثم حي.

**معيار القبول:** مراجع يترك تعليقًا على عنصر، والمطور يرى التعليق مرتبطًا بالكود، دون كسر Git workflow.

### P-13: تسليم التصميم من Figma

**الوصف:** التصميم في Figma، والتنفيذ في Tailwind، والترجمة اليدوية تسبب انحرافًا.

**الدليل:** `[سوق]` أدوات مثل Anima وLocofy وBuilder.io تستهدف هذه الفجوة.

**السبب الجذري:** Figma variables وTailwind theme نماذج مختلفة، والتصميم لا يحمل semantics.

**الحلول الحالية:**
- تصدير يدوي.
- plugins.
- AI image-to-code.

**الفرصة:**
- مزامنة tokens من Figma variables.
- استيراد إطار كصفحة أو مكون.
- مطابقة القيم مع الثيم.
- تقرير الانحراف.
- إعادة المزامنة عند تغير التصميم.

**معيار القبول:** استيراد صفحة Figma والحصول على HTML/Tailwind يستخدم tokens المشروع، مع انحراف بصري أقل من 2px في 90% من العناصر.

### P-14: هلوسة AI وعدم اتساق الكود

**الوصف:** AI يولد classes غير موجودة، قيمًا عشوائية، HTML غير صحيح، أو يعيد كتابة الصفحة كلها.

**الدليل:** `[موثق]` Pinegrow يقول إن AI لا يصيب 100%، وإنه يرسل كودًا محسنًا بسبب حدود tokens.

**السبب الجذري:** النموذج يولّد نصًا، وليس تعديلات مبنية على schema.

**الحلول الحالية:**
- مراجعة يدوية.
- prompts أفضل.
- اختبار الناتج.

**الفرصة:**
- AI يخرج patch JSON محدودًا.
- التحقق ضد theme وutility registry.
- معاينة diff قبل التطبيق.
- rollback فوري.
- قياس success rate.
- استخدام local model اختياري.

**معيار القبول:** 95% من patches AI تمر التحقق الآلي دون classes غير موجودة.

### P-15: دعم RTL والعالم العربي

**الوصف:** معظم الأدوات مبنية LTR، وتدعم RTL بشكل جزئي. Tailwind يدعم logical properties لكن التطبيق اليدوي معقد.

**الدليل:** `[فرضية]` سوق عربي كبير يعاني من أدوات لا تدعم RTL بعمق.

**السبب الجذري:** افتراض LTR في التصميم والمكونات والوثائق.

**الحلول الحالية:**
- `dir="rtl"` + logical utilities.
- مكونات مخصصة.
- تعديلات يدوية.

**الفرصة:**
- RTL أولوية في المحرر.
- معاينة LTR/RTL جنبًا إلى جنب.
- تحويل spacing/margin تلقائيًا إلى logical.
- مكتبة مكونات RTL.
- واجهة عربية كاملة.
- فحص عدم استخدام خصائص فيزيائية.

**معيار القبول:** بناء صفحة عربية كاملة دون كتابة CSS مخصص لـ RTL.

### P-16: أداء المشاريع الكبيرة

**الوصف:** آلاف الصفحات/العناصر، إعادة بناء CSS، فتح عدة views، بحث بطيء.

**الدليل:** `[موثق]` Pinegrow يحذر من كثرة page views. `[مستنتج]` أي محرر DOM ثقيل سيعاني.

**السبب الجذري:** معالجة كل المشروع في الذاكرة/الواجهة.

**الحلول الحالية:**
- إغلاق views.
- تقسيم المشروع.
- CI للبناء.

**الفرصة:**
- indexing incremental.
- workers للـ compile/scan.
- virtualized tree.
- lazy loading للمكونات.
- cache دائم.
- بناء فقط للملفات المتغيرة.

**معيار القبول:** فتح مشروع 1000 صفحة في أقل من 10 ثوانٍ، وتعديل class يعيد البناء في أقل من 200ms.

## 5. ما يجب التحقق منه في المقابلات

1. هل class soup مشكلة فعلية أم يتعايش معها المطورون؟
2. ما النسبة التي يستخدمون فيها مكونات مقابل HTML خام؟
3. هل الثيم مركزي أم موزع؟
4. كيف يختبرون responsive اليوم؟
5. ما أكثر سبب يضيع وقتهم: الأصناف، الثيم، البناء، أم المراجعة؟
