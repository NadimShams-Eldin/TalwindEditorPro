# 05 - استراتيجية المنتج

## 1. الرؤية

> **استوديو Tailwind-native لبناء مواقع كاملة، يجمع السرعة البصرية، وملكية الكود، ونظام تصميم قابل للحوكمة، وجودة مدمجة.**

المنتج ليس "Pinegrow آخر". هو إعادة تصميم لتجربة بناء المواقع حول أربع أفكار:

1. **الثيم أولًا**: كل قرار بصري يعود إلى token.
2. **المكونات أولًا**: كل تكرار يتحول إلى مكون.
3. **الجودة أولًا**: لا يُسمح بخطأ معروف أن يمر بصمت.
4. **الكود ملك المستخدم**: التصدير نظيف، ولا runtime خاص.

## 2. الشخصيات

### 2.1 "سامر" - Freelance محترف

- يبني 2-4 مواقع شهريًا.
- يعرف HTML/CSS/Tailwind.
- يستخدم Figma + VS Code + Tailwind.
- يريد تسليمًا سريعًا وكودًا نظيفًا.
- لا يريد اشتراكًا سحابيًا مرتفعًا.

**ألمه:** يعيد بناء نفس المكونات، ويضيع وقتًا في responsive ومراجعة العميل.

**ما يدفعه:** توفير 30-50% من الوقت، وتقليل المراجعات.

### 2.2 "ليلى" - مديرة استوديو صغير

- فريق 3-8 أشخاص.
- تحتاج توحيد الثيم والمكونات.
- تتعامل مع عملاء ومطورين متعاقدين.
- تحتاج مراجعة وتاريخ ونشرًا.

**ألمها:** كل مشروع يبدأ من الصفر، والجودة تختلف بين المطورين.

**ما تدفعه:** حوكمة، مكتبة مكونات، تقارير جودة، تسليم احترافي.

### 2.3 "عمر" - مطور WordPress

- يبني قوالب وblocks.
- يعرف PHP وTailwind.
- يعمل مع عملاء يحررون المحتوى.

**ألمه:** التحرير البصري في WordPress ضعيف، والـ Tailwind مع blocks معقد.

**ما يدفعه:** تحرير بصري يحافظ على PHP/HTML، ومكونات قابلة للتحديث.

### 2.4 "نورة" - مطورة منتج

- تعمل على تطبيق React/Next.
- تصميم النظام موزع بين Figma ومكونات.
- تحتاج ضمان اتساق.

**ألمها:** التصميم والكود منفصلان، وAI يولد كودًا غير متسق.

**ما تدفعه:** token sync، مكونات، مراجعة، AI مقيد.

> ملاحظة: نورة قد تكون خارج نطاق v1 إذا قررنا static-first. تبقى persona مستقبلية.

### 2.5 "خالد" - owner لمتجر/موقع

- ليس مطورًا.
- يحتاج تعديل محتوى بسيط.

**ألمه:** يعتمد على المطور لكل تعديل.

**ما يدفعه:** CMS مبسط.

> خالد ليس persona أساسيًا في v1. هو مستخدم CMS لاحقًا.

## 3. Jobs To Be Done

### JTBD-1: بناء صفحة هبوط احترافية بسرعة

- **عندما** أحصل على تصميم أو فكرة،
- **أريد** بناء الصفحة بصريًا مع Tailwind،
- **حتى** أسلّمها في وقت أقل دون التضحية بالجودة.

**العائق الحالي:** class soup، responsive، تكرار المكونات.

### JTBD-2: تغيير الهوية البصرية بسرعة

- **عندما** يطلب العميل تغيير الألوان/الخطوط،
- **أريد** تعديل tokens مرة واحدة،
- **حتى** يتحدث الموقع كله دون فوضى.

**العائق الحالي:** الثيم موزع، وحذف اللون يكسر الصفحات.

### JTBD-3: إدارة موقع كامل

- **عندما** أكمل الصفحة الأولى،
- **أريد** إعادة استخدام header/footer/مكونات،
- **حتى** لا أكرر العمل وأحافظ على الاتساق.

**العائق الحالي:** المكونات في static HTML صعبة.

### JTBD-4: تسليم كود نظيف

- **عندما** أنتهي،
- **أريد** تصدير HTML/CSS/JS نظيفًا،
- **حتى** يستطيع العميل أو فريقي صيانته دون الأداة.

**العائق الحالي:** الأدوات البصرية تضيف metadata وclasses زائدة.

### JTBD-5: ضمان الجودة قبل النشر

- **عندما** أجهز للنشر،
- **أريد** فحص HTML وaccessibility والأداء،
- **حتى** أتجنب مراجعات مكلفة.

**العائق الحالي:** الفحص منفصل ومتأخر.

### JTBD-6: العمل مع فريق

- **عندما** يعمل أكثر من شخص،
- **أريد** مراجعة وتاريخًا وتعليقات،
- **حتى** نتفق على التغييرات دون فوضى.

**العائق الحالي:** Git صعب لغير التقنيين، والسحابة تقفل الكود.

### JTBD-7: بناء موقع عربي/RTL

- **عندما** أبني موقعًا عربيًا،
- **أريد** دعم RTL أصليًا،
- **حتى** لا أكتب CSS مخصصًا لكل مكون.

**العائق الحالي:** الأدوات LTR-first.

## 4. المبادئ التصميمية

### 4.1 الشفافية

كل class، كل token، كل CSS rule يجب أن يكون قابلًا للفحص. لا سحر مخفي.

### 4.2 لا صمت

أي إجراء لا ينتج أثرًا يجب أن يشرح السبب. "لماذا لم يُطبق؟" ميزة أساسية.

### 4.3 الكود أولًا

كل ميزة يجب أن تجيب: "كيف سيبدو هذا في الكود المُصدَّر؟" إذا كان الجواب سيئًا، الميزة سيئة.

### 4.4 الثيم عقد

تغيير token عقد بين التصميم والكود. لا يجوز كسره دون impact analysis.

### 4.5 الجودة ليست وضعًا

لا يوجد "وضع فحص". الجودة حالة مستمرة لكل عنصر.

### 4.6 التدرج

المبتدئ يرى controls بسيطة. المحترف يفتح الطبقات. لا نفرض التعقيد ولا نخفيه.

### 4.7 RTL ليس إضافة

كل تخطيط وspacing واختصار يجب أن يعمل في الاتجاهين.

### 4.8 AI مساعد لا سلطة

AI يقترح patch، والمستخدم يوافق، والنظام يتحقق.

## 5. النطاق

### 5.1 MVP (الإصدار 0.1)

**الهدف:** بناء موقع static كامل واحد، من الصفر أو من قالب، وتصديره.

يشمل:

- فتح/إنشاء مشروع static.
- Tailwind v4 build مدمج.
- معاينة حية.
- Tree + Canvas + Code.
- Visual controls للخصائص الأساسية.
- Responsive breakpoints.
- Variants الأساسية (hover/focus/dark).
- Class inspector.
- Design tokens panel.
- مكونات أساسية (header/footer/card).
- Master layout واحد.
- Undo/redo.
- حفظ الملفات.
- تصدير نظيف.
- فحص أساسي: unknown classes، HTML structure، contrast.

لا يشمل:

- CMS.
- تعاون حي.
- WordPress.
- React/Vue.
- Interactions المتقدمة.
- Publish integrations.
- Plugin API.
- AI (قد يكون تجريبيًا).

### 5.2 v1.0

- مكتبة مكونات.
- Master pages متعددة.
- Assets manager.
- Pages manager.
- Forms.
- SEO tools.
- Accessibility الكامل.
- Publish إلى GitHub/Netlify/Cloudflare.
- Revisions + visual diff.
- AI patch مقيد.
- RTL كامل.
- Themes متعددة.
- Figma tokens import.

### 5.3 v2.0

- Collaboration.
- CMS.
- WordPress export.
- Plugin API.
- Component marketplace.
- React/Vue/Astro support.
- Motion editor.
- Analytics/performance budgets.

### 5.4 Non-goals

- أن نكون منصة استضافة.
- أن نكون بديل Figma.
- أن نكون no-code للجميع.
- أن ندعم كل framework في v1.
- أن نبني محرك Tailwind من الصفر.
- أن نبيع محتوى مكونات غير مرخص.
- أن نعتمد على AI لتوليد موقع كامل دون مراجعة.

## 7. نموذج التسعير المفترض

> فرضية تحتاج تحققًا. لا توجد أسعار نهائية.

### الخيار A: Open-core

- Core مجاني/مفتوح.
- Pro مدفوع: AI، publish، components، collaboration.
- Team: حوكمة وتعاون.
- Enterprise: self-hosted.

**الميزة:** انتشار سريع.
**العيب:** صعوبة تحقيق دخل مبكر.

### الخيار B: Perpetual + Updates

- ترخيص دائم.
- تحديثات سنة واحدة.
- إضافات اختيارية.

**الميزة:** يشبه Pinegrow ويجذب المحترفين.
**العيب:** دخل غير متكرر.

### الخيار C: Subscription

- شهري/سنوي.
- يشمل السحابة والتعاون.

**الميزة:** دخل متكرر.
**العيب:** منافسة قوية مع أدوات سحابية.

### التوصية المبدئية

- **Desktop core بترخيص دائم** للمحترفين.
- **Subscription اختياري** للسحابة والتعاون وAI managed.
- **Team plan** للحوكمة.
- **Free tier محدود** للتجربة.

## 10. المخاطر الاستراتيجية

1. **السوق صغير**: المحترفون الذين يريدون Tailwind + visual قد يكونون شريحة محدودة. التحقق مطلوب.
2. **Pinegrow يتحسن بسرعة**: أضاف AI وPublish وPage Health.
3. **Webflow/Framer يضيفان Tailwind**: قد يسدان الفجوة.
4. **تعقيد التنفيذ**: محرر بصري + Tailwind + AST + components = مشروع كبير.
5. **الاعتماد على Tailwind**: تغييرات كبيرة قد تكسر المنتج.
6. **التمويل**: بناء منتج ناضج يحتاج فريقًا ووقتًا.

## 11. خلاصة

المنتج يجب أن يكون **عموديًا بعمق**، لا أفقيًا بعرض. الفوز يأتي من:

- أفضل تجربة Tailwind بصرية.
- أفضل حوكمة design system.
- أفضل ضمان جودة.
- أفضل تصدير نظيف.
- دعم RTL حقيقي.

هذه الخمسة معًا تصنع منتجًا يصعب تقليده بسرعة.
