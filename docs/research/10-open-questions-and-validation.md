### تفاصيل القرارات الحرجة

#### D-01: Desktop أم Web

**لماذا الآن:** يحدد المعمارية والأمان والتوزيع.

**Desktop-first:**
- وصول مباشر للملفات وGit.
- بناء محلي بلا خادم.
- ثبات Chromium.
- خصوصية.
- عيوب: تحديثات، منصات، تعاون.

**Web-first:**
- وصول فوري وتعاون.
- عيوب: لا وصول محلي سهل، تكلفة بناء، قيود sandbox.

**التوصية:** Desktop-first، مع فصل النواة (core packages) لتمكين Web لاحقًا.

**معيار القرار:** إذا أظهرت المقابلات أن > 60% يعملون محليًا مع Git، نعتمد Desktop.

#### D-02: النطاق الأول

**الخيارات:** static HTML، WordPress، React/Next، Astro، Vue.

**لماذا:** كل إطار يضاعف تعقيد التحرير والبناء.

**التوصية:** static HTML + Tailwind v4 فقط في v1. WordPress في v1.5. الأطر في v2.

#### D-03: محرك Tailwind

**الخيارات:**
1. محرك داخلي كامل: تحكم كامل، لكن مخاطرة عالية.
2. CLI فقط: بساطة، لكن بطء وتغليف.
3. Adapter: واجهة داخلية + تنفيذ CLI + إمكانية WASM لاحقًا.
4. WASM: محمول، لكن حجم وتعقيد.

**التوصية:** adapter مع تنفيذ CLI أولًا. الواجهة تسمح بتبديل التنفيذ.

#### D-04: نموذج المكونات

**الخيارات:**
1. HTML files + placeholders.
2. JSON schema + template.
3. Web Components.
4. React-like runtime.

**التوصية:** ملفات HTML أصلية + schema منفصل + توسيع وقت البناء. الناتج HTML نظيف، والمستخدم يفهمه.

#### D-11: الاسم والعلامة

استخدام "Tailwind" في اسم المنتج قد يسبب لبسًا تجاريًا. يجب:
- مراجعة سياسة علامة Tailwind.
- اختيار اسم مستقل.
- استخدام عبارة "for Tailwind CSS" وصفًا لا علامة.

## 3. خطة التحقق

### 3.1 المقابلات (15-20)

**المشاركون:**
- 6 freelance.
- 6 وكالات صغيرة.
- 4 مطوري منتجات.
- 2 مدراء تصميم.
- 2 مطوري WordPress.

**مدة:** 30-40 دقيقة.

**المحاور:**
1. آخر موقع بنيته: العملية، الأدوات، الوقت.
2. أكبر 3 نقاط ألم.
3. كيف تدير design system.
4. كيف تتعامل مع responsive وstates.
5. كيف تراجع الجودة.
6. موقفك من AI.
7. استعدادك للدفع.
8. ما الذي يجعلك تترك أداة.

**قواعد:**
- لا تسأل "هل تحب الفكرة؟".
- اسأل عن سلوك سابق.
- اطلب أمثلة ملفات.
- لا تقدم الحل قبل فهم الألم.

### 3.2 اختبار الاستخدام

**النموذج:** Figma clickable أو HTML prototype.

**المهام:**
1. افتح مشروعًا موجودًا.
2. غيّر padding لعنصر.
3. اجعل العنصر يظهر في mobile فقط.
4. أضف hover.
5. أنشئ مكونًا من عنصر.
6. غيّر اللون الأساسي.
7. صدّر.

**القياس:**
- نجاح المهمة.
- الوقت.
- الأخطاء.
- التفكير بصوت عالٍ.
- SUS أو SEQ.

**عتبة:** 4/5 ينجحون في كل مهمة أساسية.

## 4. أسئلة مفتوحة تحتاج إجابة

### المنتج

1. هل نركز على وكالات أم freelance أولًا؟
2. هل نقدم templates أم نركز على الاستيراد؟
3. هل نحتاج marketplace في السنة الأولى؟
4. ما مستوى الاستضافة المطلوب؟
5. هل ندعم WordPress أم نؤجله؟

### التقنية

1. هل Electron كافٍ أم نحتاج Tauri؟
2. هل نستخدم CodeMirror أم Monaco؟
3. هل نستخدم parse5 أم محرك خاص؟
4. هل نبني IR كاملًا أم تدريجيًا؟
5. كيف نتعامل مع `<script>` داخل HTML؟
6. هل نستخدم Iframe أم Shadow DOM؟
7. كيف نضمن أمان المعاينة؟
8. هل نحتاج WASM compiler؟

### التصميم

1. Dark UI أم light؟
2. panels ثابتة أم عائمة؟
3. كيف نعرض variants المعقدة؟
4. كيف نعرض responsive inheritance؟
5. كيف نظهر تحذيرات Tailwind؟
6. هل نستخدم canvas واحد أم multi-viewport؟

### الأعمال

1. ما السعر؟
2. هل نبيع perpetual أم subscription؟
3. هل نقدم free tier؟
4. ما قناة التوزيع؟
5. هل نحتاج شريك استضافة؟
