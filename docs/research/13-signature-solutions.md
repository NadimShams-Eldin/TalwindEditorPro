# 13 - حلول خارج الصندوق

> كل حل هنا يبدأ من مانع موثق في `12-user-reality-and-blockers.md`، لا من قائمة ميزات. الهدف ليس "أكثر"، بل **إزالة سبب التوقف**.

## 1. كيف نقرأ هذا المستند

- **S-xx**: معرّف الحل.
- **المانع**: B-xx المرتبط.
- **الجهد**: S ≤ 2 أسابيع، M ≤ 6 أسابيع، L > 6 أسابيع لمهندس واحد.
- **الخندق**: لماذا يصعب تقليده سريعًا.
- **MVP**: هل يدخل النواة الأولى؟

## 2. الحلول

### S-01: Causal Edit Ledger — سجل التعديل السببي

**المانع:** B-02 (لماذا لم يتغير شيء؟)، B-01 (هل كسرت شيئًا؟).

**الفكرة:** كل تعديل بصري يُسجَّل ككائن واحد:

```ts
type Edit = {
  id: string;
  source: "control" | "class-tree" | "code" | "ai" | "import";
  intent: string;
  elementId: string;
  before: Snapshot;
  after: Snapshot;
  files: FilePatch[];
  effects: Effect[];
  reversible: boolean;
};
```

**كيف يعمل:**
1. الـ control لا يكتب في DOM مباشرة؛ ينتج `Intent`.
2. `Intent → ClassPatch` عبر Class IR.
3. نحسب `Effect` (computed style delta) قبل التطبيق.
4. نطبق، ونسجل كل شيء.
5. أي عنصر يمكن سؤاله: "لماذا يبدو هكذا؟" فيعرض سلسلة التعديلات.

**UX:** لوحة صغيرة "What changed?" بعد كل عملية، مع:
- الصنف المضاف/المحذوف.
- القيمة الفعلية.
- الملف/السطر.
- زر "Explain" يفتح السلسلة.

**لماذا خارج الصندوق:** الأدوات الحالية تسجل undo، لا **سبب** التغيير. هذا يحول المحرر من صندوق أسود إلى نظام قابل للتفسير.

**الخندق:** يتطلب بنية IR + source mapping + computed effects معًا. ليس ميزة يمكن إضافتها في أسبوع.

**الجهد:** M. **MVP:** نعم (نسخة مبسطة: آخر 50 تعديلًا).

### S-02: Ghost Preview — معاينة الأثر قبل التطبيق

**المانع:** B-02، B-01.

**الفكرة:** عند hover/تعديل قيمة، نعرض "شبحًا" للنتيجة على العنصر قبل الالتزام.

**كيف يعمل:**
- نحسب `Effect` دون كتابة الملف.
- نطبق overlay مؤقت داخل preview.
- نعرض delta: `padding: 16px → 24px`, `width: 320 → 352`.
- عند الإفلات، نثبّت؛ عند الإلغاء، لا أثر.

**UX:** ليس modal. شبح مباشر + tooltip صغير. زر `Tab` لتبديل "قبل/بعد".

**لماذا خارج الصندوق:** DevTools يعرض التغيير بعد تطبيقه. هنا **قبل** التطبيق، وبلغة التصميم لا CSS فقط.

**الخندق:** يتطلب محرك computed effects سريع (<16ms) داخل canvas.

**الجهد:** S-M. **MVP:** نعم للحقول الأساسية.

### S-03: Responsive Ribbon — سلم الاستجابة

**المانع:** B-04.

**الفكرة:** كل خاصية لها شريط أفقي يعرض قيمتها عند كل breakpoint، مع مصدر القيمة (موروثة/محددة).

```text
padding-x   base: 16  sm: —  md: 24  lg: —  xl: 32
             ▲ موروث    ▲ موروث   ▲ محدد   ▲ موروث  ▲ محدد
```

**كيف يعمل:**
- `ResponsiveResolver` يحسب القيمة الفعالة لكل breakpoint.
- الشريط يعرض القيم، وليس فقط الحقل الحالي.
- السحب يعدّل breakpoint محددًا، مع خيار "طبّق على الأكبر".
- النقر على قيمة يفتح محررها.

**UX:** بدل dropdown غامض، المستخدم يرى **الصورة كاملة**.

**لماذا خارج الصندوق:** Pinegrow يعرض breakpoint الحقل، لكن ليس سلم القيم كاملًا. هذا يحول السؤال من "أين أنا؟" إلى "ماذا سيحدث في كل مقاس؟".

**الخندق:** يتطلب دقة في وراثة variants و`min-width` stacking.

**الجهد:** M. **MVP:** نعم (للـ spacing/typography أولًا).

### S-04: Intent Controls + Escape Hatch

**المانع:** B-01، B-10، B-06.

**الفكرة:** المستخدم يعدّل **نية** ("مسافة مريحة"، "تباين قوي") لا صنفًا خامًا. النظام يختار class متوافقًا مع الثيم. وزر "Raw" يفتح التحكم المباشر.

**كيف يعمل:**
1. `Intent` مثل `spacing: comfortable`.
2. `IntentResolver` يقرأ tokens + scale + context.
3. ينتج `px-6` أو `gap-4` حسب الخاصية والاتجاه.
4. يعرض الصنف الناتج (شفافية).
5. Raw mode يوقف الترجمة ويسمح بأي قيمة.

**مثال:**

```text
المسافة: [مضغوطة | مريحة | واسعة]  → gap-4
النتيجة: gap-4 (16px)  [عرض الصنف] [Raw]
```

**لماذا خارج الصندوق:** الأدوات إما "visual controls" تولّد classes عشوائية، أو "design system" يفرض قيودًا. نحن نجمع: نية + شفافية + مخرج.

**الخندق:** يتطلب طبقة Intent + tokens + أمثلة سياقية. والنسخ السطحي سيبدو كـ presets.

**الجهد:** M. **MVP:** لا؛ تجربة أولًا ثم قرار.

### S-05: Class Conflict Court — محكمة التعارض

**المانع:** B-03.

**الفكرة:** عند وجود تعارض، لا نكتفي بتحذير. نعرض **من يفوز ولماذا**، ونقترح إعادة كتابة.

```text
p-4  vs  p-6        → p-6 يفوز (لاحق في الترتيب)
md:p-4 vs p-6       → md:p-4 يفوز عند md+
bg-red-500 vs bg-brand-500 → تعارض حقيقي، اختر
```

**كيف يعمل:**
- `ClassIR` + `ConflictResolver` (A-04).
- نرتب حسب: variant، specificity، source order، important.
- نعرض "winner" و"loser" بصريًا.
- إصلاحات:
  - احذف الخاسر.
  - اجعل الفائز variant.
  - استبدل الاثنين بـ token.

**UX:** لوحة "Conflicts" مع عدّاد، وشرح، و"Fix all" مع معاينة.

**لماذا خارج الصندوق:** لا أداة بصرية معروفة تشرح **سبب** فوز صنف على آخر داخل واجهة التصميم.

**الخندق:** منطق ترتيب Tailwind v4 (بما فيه variants وarbitrary) دقيق، ويحتاج اختبارات كثيفة.

**الجهد:** M. **MVP:** نعم.

### S-06: Component X-Ray + Extract Studio

**المانع:** B-05.

**الفكرة:** وضع "أشعة سينية" يرى المستخدم:
- تعريف المكوّن.
- الـ props/slots.
- الـ overrides.
- الصفحات التي تستخدمه.
- لماذا هذا الجزء مقفل.

**كيف يعمل:**
- فهرسة `componentId → instances → pages`.
- عند التحديد، breadcrumb: `Page > Section > Card (instance of components/card.html) > title (prop)`.
- زر "Open definition" ينقل للملف مع السياق.
- Extract Studio يعرض معاينة قبل الاستخراج: ما سيصبح prop، وما سيصبح slot.

**UX:** بدل الشعور بالغموض، المستخدم يرى الخريطة.

**لماذا خارج الصندوق:** الأدوات تعرض "component" ككائن مغلق. نحن نعرض **علاقته** بالنظام.

**الخندق:** يتطلب فهرسة عبر المشروع + تحليل props + تحديث آمن.

**الجهد:** M-L. **MVP:** لا؛ X-Ray في v1، Extract في v1.5.

### S-07: Build Bridge — جسر البناء

**المانع:** B-07، B-02، B-08.

**الفكرة:** "Connect build" بنقرة:
1. يكتشف المشروع (package.json، tailwind config، CSS entry).
2. يقترح أمر البناء.
3. يشغّل dev server/watch في الخلفية.
4. يراقب المخرجات.
5. يعرض حالة: `watching | building | error | stale`.
6. عند فشل، يبقي آخر CSS صالح ويشرح الخطأ.

**كيف يعمل:**
- `BuildAdapter` موحد:
  - CLI (`tailwindcss -w`).
  - npm script.
  - Vite/PostCSS.
  - custom command.
- Health check: هل ملف CSS المولّد أحدث من المصدر؟
- Drift detector: قارن hash المخرجات بالتوقّع.

**UX:** شريط أخضر "Build connected" أو أحمر "Build failing — preview is 12s old".

**لماذا خارج الصندوق:** Pinegrow يقول "external build تحت سيطرتك". نحن نجعله تحت **مسؤوليتنا المشتركة**، مع تشخيص.

**الخندق:** يتطلب فهم أنظمة بناء متعددة + إدارة عمليات + أمان.

**الجهد:** M. **MVP:** نعم لـ CLI؛ التكاملات لاحقًا.

### S-08: Import Fidelity Contract — عقد أمانة الاستيراد

**المانع:** B-01، B-07.

**الفكرة:** قبل أي تعديل على موقع قائم، ننتج تقريرًا:

```text
Files: 142 (HTML 38, CSS 12, JS 20, assets 72)
Parse: 38/38 HTML, 0 errors
Round-trip: 99.7% identical
Unsupported: inline PHP in 3 files
Risks: 2 duplicate IDs, 1 orphan asset
Mode: surgical edits only
```

**كيف يعمل:**
- Index + parse + serialize.
- Diff hash لكل ملف.
- كشف القوالب/الأطر.
- "Read-only scan" أولًا.
- بعد التعديل، diff بصري + ملفي.

**UX:** شاشة واحدة قبل البدء: "هذا ما سألمسه، وهذا ما لن ألمسه".

**لماذا خارج الصندوق:** الأدوات تقول "افتح مجلدًا". نحن نعقد **عقدًا** قابلًا للتحقق.

**الخندق:** يتطلب دقة round-trip عالية (A-08) واختبارات golden.

**الجهد:** M. **MVP:** نعم (نسخة أساسية).

### S-09: Class Diet — حمية الأصناف

**المانع:** B-10، B-01.

**الفكرة:** كشف الأنماط المتكررة واقتراح:
- مكوّن.
- `@utility`.
- token.
- حذف classes ميتة.

**كيف يعمل:**
- تجميع class strings متشابهة (A-10).
- حساب التكرار والأثر.
- معاينة "قبل/بعد" على 3 عناصر.
- تطبيق ذري + تراجع.

**UX:** "وجدنا 14 عنصرًا يكررون نفس البطاقة. استخراج مكوّن؟" مع معاينة.

**لماذا خارج الصندوق:** إعادة الهيكلة عادة يدوية وخوف. نحن نجعلها آمنة ومقاسة.

**الخندق:** جودة الاقتراح تعتمد على فهم الثيم والسياق، لا على تشابه نصي فقط.

**الجهد:** M. **MVP:** لا؛ v1.

### S-10: Token Impact Graph — خريطة أثر الرمز

**المانع:** B-06.

**الفكرة:** تغيير token يعرض:
- عدد العناصر.
- الصفحات.
- المكونات.
- لقطات قبل/بعد.
- التعارضات المحتملة (contrast).

**كيف يعمل:**
- فهرس `token → class → element → page`.
- حساب القيم المشتقة.
- معاينة تأثير على 3 صفحات.
- "Apply to all" أو "Override in component".

**UX:** "هذا اللون مستخدم في 47 عنصرًا و6 صفحات. تغييره سيؤثر على أزرار 3 مكونات."

**لماذا خارج الصندوق:** لوحات الثيم عادة تعرض swatches، لا **شبكة اعتماد**.

**الخندق:** يتطلب فهرسة دقيقة + computed style.

**الجهد:** M. **MVP:** لا؛ v1 (count + pages).

### S-11: Anchored Review + Handoff Packet

**المانع:** B-12.

**الفكرة:** تعليقات مرتبطة بعنصر/نطاق، تُخزَّن في `.tep/reviews/` ويمكن تصديرها. "Handoff Packet" = صفحة HTML مستقلة تحتوي:
- الصفحات.
- التعليقات.
- حالة الجودة.
- الـ diff.
- تعليمات النشر.

**كيف يعمل:**
- Anchor = `file + elementId + text range`.
- عند تغيير العنصر، التعليق يبقى أو يُعلَّم "stale".
- لا حاجة لخادم.
- التصدير يولد ملفًا قابلًا للمشاركة.

**UX:** العميل يفتح رابطًا/ملفًا ويرى التعليقات في مكانها.

**لماذا خارج الصندوق:** أدوات المراجعة إما سحابية ثقيلة أو صور. نحن نستخدم الملف نفسه كحامل للمراجعة.

**الخندق:** دقة anchor عبر تغييرات الكود.

**الجهد:** M. **MVP:** لا؛ v1.5.

### S-12: AI Proposal Protocol — بطاقات اقتراح

**المانع:** B-11، B-01.

**الفكرة:** AI لا يكتب ملفات. ينتج `PatchCard`:

```json
{
  "intent": "make hero more spacious",
  "confidence": 0.82,
  "patches": [
    { "op": "add-class", "target": "hero", "class": "py-24" },
    { "op": "remove-class", "target": "hero", "class": "py-12" }
  ],
  "rationale": "زيادة المسافة الرأسية تتماشى مع مقياس الثيم",
  "risks": ["قد يزيد طول الصفحة على mobile"],
  "preview": "..."
}
```

**كيف يعمل:**
1. نجمع سياقًا محدودًا: العنصر، classes، tokens، variant، siblings.
2. نطلب JSON فقط.
3. نتحقق: classes موجودة؟ tokens صحيحة؟ لا تعارض؟
4. نعرض diff + ghost.
5. المستخدم يطبق/يعدل/يرفض.
6. نسجل النتيجة لتحسين الاقتراحات.

**UX:** "اقتراح" لا "توليد". يمكن للمستخدم تعديل البطاقة قبل التطبيق.

**لماذا خارج الصندوق:** معظم AI في المحررات يولد HTML كاملًا. هنا AI **مقيد بالنظام**، ونتيجته قابلة للمراجعة.

**الخندق:** protocol + validation + context + feedback loop.

**الجهد:** M. **MVP:** لا؛ v1.

### S-13: Logical Mirror — مرآة RTL

**المانع:** B-13.

**الفكرة:** زر "Mirror" يعرض الصفحة RTL ويكشف:
- utilities فيزيائية (`ml-`, `left-`, `text-left`).
- قيمًا لا تنعكس.
- أيقونات اتجاهية.

ويقترح البديل المنطقي:
```text
ml-4 → ms-4
left-0 → start-0
text-left → text-start
```

**كيف يعمل:**
- `RTLTransformer` (A-15).
- كشف + اقتراح + معاينة LTR/RTL.
- تقرير "RTL readiness".

**UX:** ليست "نسخة عربية" منفصلة؛ نفس الصفحة باتجاهين.

**لماذا خارج الصندوق:** الأدوات تتعامل مع RTL كترجمة لاحقة. نحن نجعله **خاصية للنظام**.

**الخندق:** دقة التحويل + حالات الحافة (icons، shadows، transforms).

**الجهد:** M. **MVP:** لا؛ v1.

### S-14: Publish Confidence Score — نقاط ثقة النشر

**المانع:** B-09، B-07.

**الفكرة:** قبل النشر:

```text
Confidence: 86/100
Blockers: 0
Warnings: 3 (2 missing alt, 1 link 404)
Changed files: 12 (4 HTML, 1 CSS, 7 assets)
Preview = production build: yes
Rollback: available
```

**كيف يعمل:**
- Quality gate (A-14).
- Link crawl محلي.
- Build parity check.
- Diff manifest.
- Score = weighted checks.

**UX:** زر "Publish" يفتح تقريرًا إلزاميًا أولًا، ثم يسمح بالنشر بعد تأكيد واعٍ.

**لماذا خارج الصندوق:** النشر اليوم إما "Upload" أو CI غامض. هنا **ثقة قابلة للقياس**.

**الخندق:** يتطلب فحصًا سريعًا ودقيقًا + manifest.

**الجهد:** M. **MVP:** لا؛ v1.

**لماذا خارج الصندوق:** يجمع undo وversion control في تجربة واحدة.

## 6. معايير نجاح الحلول

كل حل يجب أن يثبت:

1. **الأثر:** يقلل زمن مهمة أو أخطاء قابلة للقياس.
2. **الشفافية:** المستخدم يفهم ما حدث.
3. **العكس:** يمكن التراجع.
4. **عدم الكسر:** لا يغير ملفات لا يقصدها.
5. **التوافق:** يعمل مع export نظيف.
