# دراسة وتخطيط منصة TailwindEditorPro

> مرحلة البحث والتصميم فقط. لا يحتوي هذا المجلد على كود تنفيذي، ولا يُعد التزامًا نهائيًا بالمعمارية قبل اعتماد القرارات المفتوحة في `10-open-questions-and-validation.md`.

- تاريخ الدراسة: 2026-10-20
- نطاق المراجعة: Pinegrow Web Editor (الإصدار 10 في الوثائق الحالية)، Tailwind CSS v4.3، وأدوات المنافسة
- لغة المستندات: العربية مع المصطلحات التقنية بالإنجليزية
- المستودع: `NadimShams-Eldin/TalwindEditorPro`

## 1. الهدف

بناء برنامج احترافي لبناء مواقع كاملة بصريًا، يكون Tailwind CSS مواطنًا من الدرجة الأولى فيه، لا مجرد إضافة لاحقة. البرنامج يجب أن:

1. يحافظ على ملكية المطور للكود الناتج، دون قفل تقني.
2. يجعل بناء صفحة كاملة أسرع من الكتابة اليدوية، دون التضحية بالتحكم الدقيق.
3. يفهم design tokens، والمكونات، والاستجابة، والحالات، والـ variants بشكل حقيقي.
4. يقلل أخطاء Tailwind الشائعة، خصوصًا class soup، والأصناف الديناميكية المفقودة، وتعقيد الثيمات.
5. يقدم جودة مدمجة: HTML صحيح، accessibility، صفحات سليمة، وأداء قابل للقياس.
6. يخدم المحترفين: وكالات، freelance، فرق منتجات، ومطوري WordPress/static sites.

## 3. الخلاصة التنفيذية

### ما يجيده Pinegrow

`[موثق]` Pinegrow ليس أداة تصميم بصري بالمعنى السطحي. هو محرر HTML/CSS حقيقي يعمل على ملفات المشروع مباشرة، ويجمع التحرير البصري مع الكود، ويدعم static HTML وWordPress وTailwind، ويضيف نظام Actions وComponents وMaster Pages وCMS مبسط وAI Assistant وPublish.

أهم نقاط قوته:

- ملكية الكود: الملفات تبقى HTML/CSS/JS عادية.
- العمل على مواقع قائمة، وليس فقط مشاريع جديدة.
- عمق تحرير CSS وHTML، مع تحكم دقيق.
- نظام مكونات قابل للتحديث، وeditable areas.
- دعم Tailwind بصري متقدم، بما في ذلك Class Tree وDesign Panel وComponent Styles.
- لا يعتمد على السحابة، وهو مناسب لمن يريد الخصوصية.

### أين توجد الفجوة

`[مستنتج]` Pinegrow ممتاز لمن "يعرف HTML/CSS ويريد أدوات بصرية فوق الكود". لكنه يترك فجوات كبيرة للمحترفين:

1. **Design system ليس مواطنًا أولًا.** الثيم موجود في Design Panel، لكن إدارة الرموز والقيود والمراجعة عبر المشروع ليست بنفس عمق أدوات design systems الحديثة.
2. **تجربة الاستخدام ثقيلة وتتطلب تعلمًا.** الوثائق نفسها تقول إن الأداة ليست مناسبة لمن لا يعرف HTML/CSS.
3. **Tailwind ليس Native بالكامل.** هناك قيود موثقة: variants غير المفعلة تظهر بلا تأثير، Class Tree لا يضيف/يعدل class styles، Component Styles لا تعمل مع external build، وقائمة used classes لا تنظف نفسها.
4. **الجودة والمراجعة متأخرة عن البناء.** Page Health وAccessibility موجودان في Pinegrow 10، لكنهما أدوات فحص وليست قيودًا تصميمية تمنع الخطأ أصلًا.
5. **التعاون الحي غائب.** لا يوجد real-time collaboration موثق بمستوى الأدوات السحابية.
6. **التكامل مع الأنظمة الحديثة محدود.** static وWordPress وVue Designer، لكن لا توجد منصة موحدة لـ React/Vue/Astro/Svelte مع design system وحوكمة.
7. **الـ AI غير مقيد ببنية design system.** حسب الوثائق، الـ AI Assistant يعيد HTML/كود، مع تحسينات، لكنه ليس محرك تعديلات semantic مضمون ضد الأصناف غير الموجودة.

### الفرصة

الفرصة ليست في نسخ Pinegrow. الفرصة في بناء:

> **استوديو Tailwind-native للمحترفين، token-first وcomponent-first، يضمن كودًا نظيفًا قابلًا للتصدير، ويجعل الجودة والاستجابة ونظام التصميم قيودًا داخلية لا خيارات لاحقة.**

التمايز المقترح:

| المحور | Pinegrow | الفرصة لنا |
|---|---|---|
| نموذج التحرير | DOM/كود + أدوات بصرية | نفس النموذج، لكن مع IR للأصناف وdesign tokens |
| Tailwind | إضافة قوية مع قيود | محرك أصلي يفهم theme وvariants وconflicts |
| نظام التصميم | Design Panel جيد | token graph + قيود + مراجعة + مزامنة Figma |
| إعادة الهيكلة | يدوية غالبًا | كشف class soup واقتراح مكونات/أنماط |
| الجودة | فحص بعد البناء | قيود أثناء التحرير + فحص مستمر |
| التعاون | محدود/غير موثق | سحابة اختيارية + CRDT لاحقًا |
| الجمهور | مطور يعرف HTML/CSS | محترف يريد سرعة + حوكمة + كود نظيف |

### الحلقة الثقة

`[مستنتج]` من شكاوى المستخدمين الموثقة (منتدى Pinegrow، Stack Overflow، GitHub) أن المانع الحقيقي ليس نقص اللوحات، بل انقطاع الثقة في ثلاث لحظات: قبل التعديل ("هل سيكسر الكود؟")، وأثناءه ("لماذا لم يتغير شيء؟")، وبعده ("هل ما أراه هو ما سأنشره؟"). لذلك وعد المنتج هو:

> **كل تعديل مشروح، قابل للتراجع، وقابل للتسليم.**

هذا الوعد يترجم إلى حزمة أولى: كشف بالبصمة، عقد أمانة الاستيراد، سجل تعديل سببي، معاينة أثر، محكمة تعارض، وجسر بناء. التفاصيل في `12-user-reality-and-blockers.md` و`13-signature-solutions.md` و`14-relationship-map.md`.

## 6. ما لا يغطيه هذا المجلد

- لا يحتوي على كود إنتاجي أو scaffold.
- لا يحدد هوية بصرية نهائية أو اسمًا تجاريًا نهائيًا. الاسم الحالي هو اسم المستودع العامل فقط، ويجب مراجعة استخدام علامة Tailwind التجارية قانونيًا.
- لا يفترض نتائج مقابلات لم تُجرَ بعد.
- لا يعد خطة تسويق كاملة أو خطة مالية تفصيلية.
- لا يقرر دعم React/Vue/Astro في v1؛ هذا قرار مفتوح.

## 7. الخطوة التالية

1. اعتماد أو تعديل القرارات في `10-open-questions-and-validation.md`.
2. تنفيذ 15-20 مقابلة مع المطورين والوكالات للتحقق من ترتيب الألم.
3. بناء نموذج أولي عالي الدقة (Figma أو HTML) لثلاثة تدفقات: استيراد موقع، بناء صفحة، إنشاء مكون.
4. بعد الاعتماد فقط، ننتقل إلى `writing-plans` لخطة تنفيذ تفصيلية.

## 8. نتائج الاختبارات التقنية

نُفذت ثلاث تجارب تقنية مع 26 اختبارًا آليًا في `spikes/`:

- تعديل HTML جراحيًا يحافظ على الملف بايتيًا، ويجعل إضافة/إزالة class قابلة للعكس.
- تشغيل Tailwind v4 برمجيًا مع candidate set صريحة يعالج فجوة الأصناف الديناميكية.
- تبديل CSS في المعاينة يحافظ على العناصر والتحديد.

التقرير الكامل والأرقام والقيود في `spikes/REPORT.md`. أهم نتيجة: إعادة تحليل HTML لكل تعديل تقترب من ميزانية 100ms، لذلك الخطوة التالية فهرس مستند دائم.
